## Synthesis
The research reveals a fragmented and restrictive landscape for CLI agent authentication across major AI providers, with critical distinctions between OAuth suitability and API key viability that directly inform the design of Cercano’s setup wizard. For OpenAI, OAuth 2.0 is technically feasible via the Authorization Code flow with narrow scopes (`chat.completions`, `davinci`), but its practicality for an open-source CLI agent is severely undermined by ambiguous enforcement: hard, opaque rate limits (3,000 RPM / 1M TPM) trigger HTTP 429 errors without retry guidance or usage metrics—precisely the kind of invisible throttling that disrupts autonomous agent workflows. Moreover, while no explicit prohibition against third-party use of OAuth tokens exists in the archived ToS, the deprecation of Codex and lack of fine-tuning or file-access scopes signal that OpenAI intends OAuth to serve only interactive, user-facing applications—not long-running or programmatic agent sessions. Given these operational hazards, the cleanest path for Cercano’s wizard is to present API keys as the primary OpenAI option, supplemented with a clear warning about rate-limit unpredictability.

Google’s ecosystem presents a more infrastructure-focused but legally and technically constrained picture: while no dedicated CLI-agent OAuth flow exists for Gemini, VPC Service Controls demonstrate Google’s emphasis on perimeter-based security—making service account keys the dominant pattern for programmatic access. However, these keys are tied to VPC-network-bound perimeters, which block non-VPC traffic, including most CLI environments unless users meticulously configure firewall rules or enable private.googleapis.com access. This implies that, for a local-first CLI tool, API keys (not OAuth) remain the only reliable option for most users, though service account key rotation and VPC constraints must be clearly documented in the wizard to prevent misconfiguration. Microsoft and other providers like Mistral and Groq, by contrast, embrace gateway-centric architectures (e.g., Azure API Management with Entra ID), where OAuth 2.0 via Authorization Code + PKCE is not only supported but recommended—even for native or CLI clients—as long as the implementation adheres to modern security practices. Crucially, Microsoft’s own guidance mandates PKCE for all public clients and explicitly rejects less secure grants (like implicit or password-based), meaning Cercano’s wizard should prioritize OAuth with PKCE for providers offering it (e.g., Azure OpenAI), while defaulting to API keys where OAuth is either unavailable or operationally untenable (OpenAI, non-VPC-enabled Google services). Collectively, these findings indicate that no single provider offers a seamless, open-CLI-friendly OAuth experience: the wizard must tier options by reliability—OAuth-only where ToS explicitly permits and PKCE is enforced (Microsoft), API keys with warnings where throttling is punitive and opaque (OpenAI), and service-account caveats where network isolation is mandatory (Google).
