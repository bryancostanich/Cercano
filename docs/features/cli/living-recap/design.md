# Living Recap — Design

**Status:** Implemented. Store column, debounced local-only generator, proto +
`GetConversation` RPC, agentclient, and CLI rendering (footer, history picker,
resume banner) are all in place. Recap regeneration is scheduled on both
persistence paths — the legacy SmartRouter path (inside the agent) and the
native tool-loop path (via `Agent.ScheduleRecap` from the streaming server).

A one-line, continuously-maintained summary of the work in a Cercano CLI/agent
session — analogous to Claude Code's "recap." It is generated locally, persisted
with the conversation, and shown live in the chat footer, in the history picker,
and on resume.

## Goal

Give the user an at-a-glance "what got done" line per conversation that:
- evolves as work progresses ("living"),
- is generated by the **local model only** (zero-cost, private),
- is persisted in the conversation DB with the rest of the context,
- surfaces in three places: chat footer (live), history picker (per row), resume banner.

Distinct from the conversation **Title**, which is algorithmically derived from the
first user prompt and stays fixed. The recap is LLM-generated and changes over time.

## Architecture (Approach A)

Generation lives **server-side** in the agent (it owns the local engine and the
store). The CLI displays the recap and refreshes it on turn boundaries. Other
clients (VS Code, Zed) get the recap for free via the same RPCs.

```
turn completes ─► agent persists turn ─► recapGen.Schedule(convID)
                                              │ debounce (<= once / N s)
                                              ▼
                                   local engine: prior recap + recent turns
                                              │  -> one line
                                              ▼
                                   store.UpdateRecap(convID, line)

CLI footer / picker / resume ──GetConversation(convID)──► latest recap
```

## 1. Data model — `internal/conversation/store.go`

- Add columns to `conversations`: `recap TEXT`, `recap_updated_at INTEGER` (unix secs).
- Migration: idempotent `ALTER TABLE conversations ADD COLUMN ...` in `Open()`,
  ignoring "duplicate column name" errors so existing DBs migrate in place.
- `Info` struct gains `Recap string` and `RecapUpdatedAt time.Time`; `List` selects them.
- New API:
  - `UpdateRecap(ctx, conversationID, recap string) error` — sets recap + recap_updated_at.
  - `Get(ctx, conversationID) (Info, error)` — single-conversation fetch (footer
    refresh + resume) without rehydrating turns.

## 2. Proto / RPC — `source/proto/agent.proto`

- `Conversation` message: add `string recap = 8;` and `int64 recap_updated_at = 9;`.
- New RPC: `GetConversation(GetConversationRequest{ conversation_id }) returns (Conversation)`
  — lightweight fetch for the footer and resume.
- `agentclient.Client.GetConversation(ctx, id) (ConversationInfo, error)`;
  `ConversationInfo` gains `Recap`, `RecapUpdatedAt`.

## 3. Generation — `RecapGenerator` (new, agent server side)

- Agent calls `recapGen.Schedule(conversationID)` immediately after a completed
  turn is persisted (same site as turn persistence).
- Debounce: per-conversation, mutex-guarded timer map; fires at most once every
  `recapDebounce` seconds (const, ~8s). Rapid turns coalesce into one generation.
- On fire (async goroutine):
  1. Load prior recap + last K turns from the store.
  2. Call the **local engine only** (never escalate to cloud) with a tight prompt:
     *"In one line, past tense, <= 80 chars, summarize what this coding session
     accomplished. Prior recap: <prior>. New activity: <turns>. Output only the line."*
  3. Persist via `store.UpdateRecap`.
- Incremental (prior recap + new turns, not full history) keeps it cheap and
  genuinely living. Input is truncated/capped before the call.
- Output sanitized to a single line and length-capped.

## 4. CLI display — `internal/cli/ui/model.go`, `history_picker.go`

- **Footer:** dimmed recap line at the bottom of the chat area, above the input,
  rendered only when no overlay (history picker / config editor / confirm) is
  active. Truncated to terminal width.
- **Refresh:** after a turn completes and when an overlay closes, issue a
  `GetConversation` command and update the footer. The value may be up to one
  debounce window stale — accepted under Approach A.
- **History picker:** per-row summary uses the recap when present, else falls back
  to the derived title (current behavior).
- **Resume:** print a one-line `Recap: ...` banner before continuing the session.

## 5. Error handling

- Generation failure (local model down / timeout): log at debug, keep the prior
  recap, never block a turn or surface an error to the user.
- No recap yet: footer shows nothing; picker falls back to title; resume prints nothing.
- Migration tolerates pre-existing columns; `UpdateRecap` is a single guarded UPDATE.
- Concurrency: per-conversation debounce guarded by a mutex; generation runs in its
  own goroutine and does not hold request-path locks.

## 6. Testing

- **store:** migration adds columns on an existing DB; `UpdateRecap` round-trips;
  `List` / `Get` return recap.
- **generator:** N rapid `Schedule` calls within the window coalesce to one
  generation; incremental prompt is built from prior recap + new turns; local-only
  (mock engine asserts no cloud path); engine failure preserves the prior recap.
- **CLI:** footer hidden under overlay, shown otherwise, truncated to width; picker
  uses recap-or-title fallback.
- **client:** `GetConversation` returns the recap field.

## Decisions / constraints

- Local model only — recap is a convenience and must stay zero-cost and private.
- Debounce interval, K (turns of context), and the ≤80-char cap are constants for
  the first version; per-model configuration is out of scope (see existing
  "Per-Model Configuration" improvement).
- Streaming push of recap updates (Approach B) is deferred; turn-boundary refresh
  is sufficient for v1.
