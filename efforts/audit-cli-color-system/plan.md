# Plan: centralize CLI colors behind theme tokens

## Design choice

The approved boundary is **named tokens plus centralized derived colors**:
render code may request semantic styles or derived theme colors, but it may not
spell product colors directly. The theme package owns raw palette literals,
contrast decisions, interpolation endpoints, and reusable color math.

| Decision axis | Strict named tokens only | Named tokens plus centralized derived colors | Current style plus spot fixes |
|---|---|---|---|
| Cost | Medium: many one-off computed shades become palette fields. | Medium: move literals and helpers into `theme`, then wire render paths to semantic APIs. | Low: only change current visible issues. |
| Risk | Low runtime risk but high naming bloat. | Low-to-medium: derived helpers need tests, but semantics stay clean. | Medium: future daylight regressions remain likely. |
| Reward | Very easy to audit mechanically. | Clean architecture and still flexible for fades, animation ramps, and contrast-aware styles. | Fast but not systemic. |
| Side effects | Palette grows with narrowly named fields. | Theme package becomes the single color boundary. | Leaves inconsistent conventions. |
| Chosen? | No. | Yes. | No. |

### 1. Establish theme-owned semantic tokens

Add missing named fields to `theme.Palette` and/or `theme.Styles` for surfaces
that currently depend on literals:

- selection background;
- code block canvas;
- bypass flag foreground/background;
- activity spinner base/peak;
- activity text base/peak for dark and light themes, or a helper that derives
  them from named palette fields;
- compacting meter contrast text/background semantics if not already expressible
  through existing styles.

Keep the palette fields semantic, not screenshot-specific. Prefer names like
`SelectionBg`, `CodeBlockBg`, `DangerText`, `ActivityBase`, `ActivityPeak`, and
`MeterLabelOnFill` over names like `Slate58829E`.

### 2. Move color math into the theme package

Move or replace these UI-local helpers from `internal/ui/model.go` with
`internal/theme` equivalents:

- `fadeColor`
- `colorRGB`
- `rgbColor`
- `isLightColor`
- the activity/progress interpolation color selection currently embedded in
  `progressColorAtForPalette`

Target API shape can be small and practical, for example:

- `theme.Fade(c color.Color, factor float64) color.Color`
- `theme.IsLight(c color.Color) bool`
- `theme.Lerp(a, b color.Color, t float64) color.Color`
- `theme.ContrastTextFor(bg color.Color, lightText color.Color, darkText color.Color) color.Color`
- `theme.ActivityColorAt(p Palette, col int, sweepPos float64, tail float64) color.Color`

Do not overbuild a full color engine; keep only helpers needed by current UI
surfaces.

### 3. Replace render-layer hardcoded colors

Update render/UI code so it consumes theme-owned styles/helpers:

- `selection.go`: replace the hardcoded `selectionBg` ANSI constant with a
  theme-derived selection highlighter. Because selection highlighting currently
  reasserts raw SGR after each inner SGR, either:
  - build the SGR from `theme.SelectionBg` through a theme helper, or
  - pass a `lipgloss.Style`/SGR string generated by `theme` into the selection
    path.

  The preferred implementation is to keep the SGR reassertion mechanism but
  make the SGR string come from `theme.SelectionBackgroundSGR(p)` so the color
  is named and theme-owned.

- `model.go`: replace hardcoded spinner amber endpoints and lime/white activity
  endpoints with `theme` helpers. The animation timing and layout can stay in
  UI; color choice moves to theme.

- `model.go` compacting meter: replace inline light-theme contrast decisions
  with a theme helper or style such as `styles.MeterLabelOnFill` /
  `theme.MeterLabelForeground(p, onFill bool)`.

- `styles.go`: replace anonymous literals inside `NewStyles` with named palette
  fields where appropriate (`CodeBlockBg`, bypass flag foreground, etc.).
  Literals can remain in `builtins.go` because that is the palette definition.

### 4. Add a static audit test

Add a focused test, likely under `source/clients/cli/internal/theme` or
`source/clients/cli/internal/ui`, that scans relevant source files and rejects
new product hardcoded color usage.

Suggested behavior:

- Scan `.go` files under `internal/ui` and `internal/render`.
- Flag:
  - `#[0-9A-Fa-f]{6}`;
  - `38;2` / `48;2` literal fragments;
  - `lipgloss.Color("...")` with a string literal;
  - raw RGB endpoint arrays used for color values;
  - `Faint(true)` outside an allowlist.
- Allow test files to contain expected ANSI fragments, but consider scanning
  non-test files only for the first pass.
- Allow generated/probe files only if they do not ship; ideally no allowlist is
  needed for product files after this cleanup.

The test should print actionable file:line diagnostics so future fixes are
straightforward.

### 5. Preserve and extend regression coverage

Keep existing tests from the recent daylight fixes and add/adjust focused tests
for the new theme contract:

- selection background SGR is generated from the daylight palette;
- activity spinner/sweep colors come from theme helpers rather than hardcoded
  endpoints;
- compacting meter label has readable foreground/background on daylight;
- static audit fails on representative disallowed patterns.

Refresh goldens only where visible ANSI output intentionally changes.

## Risks and mitigations

- **Selection highlighting is SGR-sensitive.** It reasserts background escapes
  after nested ANSI changes. Preserve that mechanism; only move the color source
  into `theme`.
- **Animation colors may subtly change.** Keep dark-theme defaults visually close
  to current cracker behavior by moving current endpoints into named cracker
  palette fields first, then deriving daylight-safe values explicitly.
- **Palette bloat.** Use semantic fields for real UI roles. Put computed shades
  behind helpers instead of creating fields for every intermediate color.
- **Static audit false positives.** Start with non-test product files and a tiny
  allowlist. The goal is to block regressions without fighting legitimate theme
  definitions.
